# 0.5.0 提案：判据断言化 + 审计报告字段对齐 + 弹窗/等待策略

> 状态：**P0 / P1 / P2 已实现，随 `0.5.0` 发布** · P3 计划在 `0.6.x` · 作者：DSH + DwGuard
> 前置：`0.4.2`（npm `dwguard-dsh-hmos@0.4.2`，SDK 26 / devecocli 1.3.10 环境已验证）

## 0. 为什么做

当前 `dwguard_spec` 的判据是「自然语言陈述 + 验证方式」，`dwguard_audit` 的检查只有 `result + evidence`。这带来三个问题：

1. **判据不可执行**：同一条「间距 12vp」判据，两个审计员可能给出相反结论；
2. **证据不可复核**：`evidence` 是自由文本，机器无法判断「1200ms」是否满足「≤ 800ms」；
3. **报告不可消费**：审计结论埋在 markdown 里，CI/回归无法按字段读取。

P0 的目标：**让每条写得出数值的判据自带可执行断言，让审计闸门自己重算结论**——人工只负责「取实测值 + 附证据」，不再由人裁决是否通过。

## 1. 总览与优先级

| 阶段 | 内容 | 破坏性 | 版本 |
| --- | --- | --- | --- |
| **P0（已实现）** | 判据 `assertion`（matcher）+ 审计 `actual` + 闸门自动判定 + 报告字段 | 向后兼容（字段可选） | `0.5.0` |
| **P1（已实现）** | 审计剧本模板：beforeAll/afterAll、`waitForIdle`、重试、弹窗规则库（借鉴 Hypium `pop_up_window_handler`） | 文档 + skill | `0.5.0` |

| P3 | 设备矩阵：**串行设备池**（一次一台，跑完 stop；子代理并行、设备操作互斥） | 配置 + 调度 | `0.6.x` |

> P3 不做「4 台模拟器同时开」：本机 16GB，单台模拟器实测工作集 ~2.7GB（实例配置 `hw.ramSize=4096`、`hw.cpu.ncore=4`），4 台并发需 ≥32GB 且会干扰性能取证。方案是 `devicePool + maxConcurrency=1` 的串行轮转，内存等于单台。

## 2. P0 数据模型

### 2.1 `Criterion.assertion`（可选）

```jsonc
{
  "id": "P-01",
  "dimension": "performance",
  "statement": "冷启动到首帧 ≤ 800ms",
  "verify": "Profiler 启动分析毫秒数",
  "weight": "must",
  "ruleId": "DW-PERF-01",
  "assertion": {
    "matcher": "lte",     // equals | contains | regex | range | gte | lte | oneOf | present
    "expected": 800,
    "unit": "ms",         // 仅文档展示
    "source": "Profiler 冷启动"  // 实测值从哪里取（可选）
  }
}
```

| matcher | 语义 | 必填字段 |
| --- | --- | --- |
| `equals` | 实测值等于期望值（数值优先数值比较，字符串精确比较） | `expected` |
| `contains` | 实测值包含期望子串（大小写不敏感） | `expected` |
| `regex` | 实测值命中正则（未加锚点，按需自行 `^$`） | `expected`（合法正则） |
| `range` | 实测值 ∈ [min, max]（含边界） | `min` 和/或 `max` |
| `gte` / `lte` | 实测值 ≥ / ≤ 期望数值 | `expected`（数字） |
| `oneOf` | 实测值等于列表之一 | `expected`（非空数组；模型可传 JSON 数组字符串） |
| `present` | 实测值非空 | — |

**数值解析**：数值类 matcher 取 `actual` 里的第一个数字，所以实测值可以带单位——`"12vp"` → 12，`"720ms"` → 720，`"4.9:1"` → 4.9。

### 2.2 `Check.actual`（审计必填，当判据有 assertion）

```jsonc
{
  "criterionId": "P-01",
  "result": "pass",
  "evidence": "3 次冷启动 700/720/760ms，截图 artifacts/perf.png",
  "actual": "720ms"
}
```

审计工具会把 `assertion + actual` 重算出的结论写进 `Check.assertionVerdict`（`pass` / `fail`），并进入 `audit-<n>.json` / 报告表格。

## 3. P0 闸门规则（`dwguard_audit`）

| 场景 | 处理 |
| --- | --- |
| 判据有 assertion，check 判 `pass` 但缺 `actual` | **error**（断言未执行不得判 pass） |
| 判据有 assertion，check 判 `pass`，但断言重算为 `fail` | **error**（自相矛盾，拒绝审计） |
| 判据有 assertion，check 判 `fail`，但断言重算为 `pass` | **warning**（可能还有其它证据导致失败，提示复核） |
| 判据有 assertion，check 判 `unverified` 且缺 `actual` | warning（must 判据本身已由既有闸门判 error） |
| 判据无 assertion | 保持原行为（人工判定 + 证据） |
| assertion 本身非法（matcher 未知、range 无边界、正则不合法…） | `dwguard_spec` **拒绝写入**（`E_CRITERION_ASSERTION_INVALID`） |

其它配套：

- `dwguard_spec` 对「must + 陈述含数字 + 无 assertion」给出提醒 `W_CRITERION_NO_ASSERTION`；
- `tasks/spec.md` / Goal 简报新增「断言」列；
- `audit-<n>.md` 新增「断言 / 实测值 / 断言判定」列；
- `acceptance-report.md` 证据索引新增「断言 / 实测值」列；
- 返工单新增「闸门问题」小节（以前只有失败项，断言矛盾这类闸门错误看不到）。

## 4. P0 验收标准（可证伪）

| ID | 判据 | 验证方式 |
| --- | --- | --- |
| P0-A | 带合法 assertion 的判据可写入，`spec.json` 保留 assertion，`spec.md` 出现「断言」列 | `npm test` 中 `spec freezes machine-checkable assertions…` |
| P0-B | 非法 assertion（range 无边界 / 正则不合法）被拒且不写文件 | `spec refuses an invalid assertion…` |
| P0-C | 断言一致时审计通过，`audit-1.json` 的 checks 带 `assertionVerdict=pass` | `audit recomputes assertions…` |
| P0-D | 断言不通过但标 pass → 审计被拒，返工单含「断言判定不通过」 | `audit refuses a pass that contradicts…` |
| P0-E | 断言判据缺 `actual` 但标 pass → 审计被拒 | `audit refuses a pass without the required actual…` |
| P0-F | 原有 49 个用例 + 新增断言用例全绿 | `npm test`（见下方记录） |
| P0-G | 零行为的旧任务包（无 assertion）行为不变 | 原有 workflow/gates 测试 |

实测记录（本地，2026-11-02）：`npm run typecheck` 0 错误；`npm test` **55/55 通过**（原 49 + 新增 6）。

## 5. P1：审计剧本模板（已实现）

借鉴 Hypium 的生命周期/等待/弹窗设计，已落到 `skills/hmos-audit-playbook.md` §12：

1. **beforeAll / afterAll**：安装包固定（记录 HAP sha256）、清应用数据、确定字体档/深浅色、开始前截图基线；
2. **waitForIdle + 重试**：截图前等 UI 稳定（`devecocli ui wait` + 连续两次 layout 一致），失败最多重试 2 次并写 `attempt=n/3`；
3. **超时**：每个取证动作显式超时（`hdc` / `devecocli` 命令均带 timeout），超时记 `unverified` 而不是 `fail`；
4. **弹窗规则库**：隐私协议 / 权限 / 升级 / 锁屏的识别与处理规则（借鉴 `pop_window_rules`），关不掉时截图 + 记 `blocker`；
5. **报告字段**：本轮先在 `checks[].note` 记录设备 / attempt；`device` / `durationMs` 结构化字段留给 P3 的矩阵改造。

## 6. P2 / P3（后续）

- **P2（已实现）**：交互轨迹采集已落到 `docs/perf-baseline.md` §4——用 `hidumper RenderService fps / hitchs` 取外部可观测数值、`hitrace` 抓系统 trace 作复核材料、点击→可用布局耗时作 `actual`；App 内 `hiTraceMeter` 埋点仅作辅助，不能作为唯一依据；
- P3（计划，已细化到 0.6.0 计划）：`config.devicePool = [{ sn, type, apiLevel }]` + `maxConcurrency`（默认 1，串行轮转），`dwguard_audit` 的 `device` 字段记录本轮设备；四维子代理并行、设备操作加互斥。详见 `docs/0.6.0-plan.md`。

## 7. 兼容性与迁移

- `assertion` 与 `actual` 都是**可选字段**：老任务包（0.4.x 写入）可继续使用，闸门行为不变；
- `parseTaskPack` 会保留被手改/旧文件中的 assertion（非法 assertion 在 `action: validate` 时报 `E_CRITERION_ASSERTION_INVALID`）；
- 旧版插件读新 `spec.json` 会忽略未知字段（JSON 宽松解析），不会崩；
- 语义化版本：新增可选字段 → `0.5.0`（minor）；
- 发版沿用现有流程：`npm run release -- --bump=minor` → 提交 → `git tag v0.5.0 && git push origin v0.5.0` → CI 用 OIDC trusted publishing 自动发布并附 provenance。
