# 0.6.0 计划：设备池（P3）+ 审美学习

> 状态：**方案（待实现）** · 目标版本：`0.6.0` · 前置：`0.5.0`（断言化 + 取证剧本 + 交互轨迹）
> 范围：P3（串行设备池 + 设备字段）+ 审美学习 v1（审美偏好档案 / 视觉基线 / 学习闭环）。

## 0. 为什么是这两件事

`0.5.0` 解决了「判据可执行」（assertion + actual）和「证据怎么取」（剧本 + 交互轨迹）。还剩两个结构性缺口：

1. **单设备假设**：`dwguard_audit` 只记录一轮检查，不记录「在哪些设备/API/字体档上取的证」；多设备矩阵只能靠人肉串行，结果无法机器复核，也无法回答「这条判据覆盖了几台设备」。
2. **审美维度没有记忆**：功能/性能/无障碍可以靠断言和数值回归，审美判据（间距、圆角、字号阶、配色、密度、动效）每轮都要重新争论；用户确认过的审美选择没有沉淀成下一轮的基线，`dwguard_calibration` 只能统计漏检率，不能改进行为。

0.6.0 的目标：**设备维度可配置、可排队、可追溯；审美判断有档案、有基线、能从用户反馈中学习。**

## 1. P3：串行设备池

### 1.1 设计原则

- **子代理并行、设备串行**：四维审计子代理可以同时跑，但设备操作串行排队（互斥锁 + 队列），内存占用等于单台设备；
- **默认 `maxConcurrency = 1`**：本机实测单台模拟器工作集 ~2.7GB（`hw.ramSize=4096` / `hw.cpu.ncore=4`），16GB 主机并发 4 台需 ≥32GB 且会污染性能取证；真机补位优先；
- **设备身份进证据**：每条 check 记录在哪台设备取的证，性能类判据强制「设备独占、无并发模拟器」。

### 1.2 配置与数据模型

```jsonc
// 插件配置（cordis.patch.yml 的 config 段）
{
  "devicePool": [
    { "sn": "127.0.0.1:5555", "type": "phone",    "apiLevel": 24, "kind": "emulator" },
    { "sn": "FMR0223C13000829", "type": "phone",  "apiLevel": 26, "kind": "real" }
  ],
  "maxConcurrency": 1,
  "deviceLockTimeoutMs": 600000
}
```

- `devicePool`：空 = 不启用矩阵（保持 0.5.0 行为，单设备）；
- `maxConcurrency`：默认 1；>1 时只允许 `kind: real` 的设备（模拟器并发告警）；
- 设备锁落在 `.shared/.device-lock.json`（`{ sn, acquiredAt, holder }`），超时释放并记警告。

### 1.3 行为

1. `dwguard_deveco` 新增 `device` 参数（缺省 = 池中第一台空闲设备）；`device` 动作返回池状态（在线/占用/API/类型）；
2. `dwguard_audit` 的 `checks[]` 新增 `device`（可选，启用池时必填）；报告把「判据 × 设备」展开成矩阵；
3. 性能判据（`DIMENSION_EVIDENCE.performance`）在池模式下令牌唯一：取证期间禁止其他设备占用（性能噪声控制）；
4. `dwguard_status` 显示设备队列（当前占用/等待数）；
5. 每轮审计在 manifest 里写 `devices: [{sn, type, apiLevel, fontScale, theme}]`，验收报告附录给矩阵表。

### 1.4 验收标准（可证伪）

| ID | 判据 | 验证方式 |
| --- | --- | --- |
| P3-A | 配置 2 台设备、`maxConcurrency=1` 时，两次并发取证串行执行，总耗时 ≈ 两者之和 | 单测：假 clock + 两个并发 `acquire()`，断言顺序与耗时 |
| P3-B | 设备被占用超时（`deviceLockTimeoutMs`）后锁被释放并写警告 | 单测：占用后不释放，推进假时钟，断言锁文件被清理 |
| P3-C | 启用池时，审计缺少 `checks[].device` → 闸门拒绝 | 单测：audit 输入缺 device，断言 error 文案 |
| P3-D | 验收报告含「判据 × 设备」矩阵，manifest 记 `devices[]` | 单测：读 acceptance-report.md / audit.json |
| P3-E | `maxConcurrency>1` 且池中有模拟器 → 启动告警并降级为 1 | 单测：配置校验 |

## 2. 审美学习 v1

### 2.1 问题

- 审美判据（`DW-AES-*` 21 条）依赖人，每轮重新讨论；
- 用户确认过的选择（主色、圆角、间距节奏、字号阶、深色模式策略、动效时长）没有被记录；
- 截图对比靠肉眼，没有基线；「这轮比上轮丑了」无法回归；
- `dwguard_calibration` 的 miss 只统计，不反哺规则。

### 2.2 数据模型

**审美偏好档案**：`knowledge/aesthetic-profile.md`（项目级，Markdown 表格 + 可解析 JSON 块）：

```jsonc
{
  "version": 1,
  "updatedAt": "2026-11-02T...",
  "decisions": [
    {
      "id": "AES-PALETTE-01",
      "area": "palette",            // palette | spacing | radius | type | density | motion | dark | icon | card
      "decision": "主色 #0A59F7，强调色 #E84026，中性灰阶 5 档",
      "source": "confirmation-3",   // 用户确认/驳回/审计发现
      "confidence": 0.8,            // 0–1，确认 +0.1，驳回 -0.2
      "assertionTemplate": { "matcher": "equals", "expected": "#0A59F7" },
      "updatedAt": "..."
    }
  ]
}
```

**视觉基线**：`artifacts/visual-baseline/<specVersion>/`：

```text
index.json                 # 页面/状态 → 证据文件 + 关键数值
<page>.<state>.png         # 截图（人复核）
<page>.<state>.bounds.json # 布局树抽取：节点 id/bounds/fontSize/padding/radius 数值
```

- 基线在**用户确认后**写入（`dwguard_confirm` 挂钩），不覆盖已有基线，按 `specVersion` 目录隔离；
- 比对不依赖图像解码库：先用 `bounds.json` 做**数值 diff**（允许阈值：间距 ±2vp、字号 0、圆角 ±2vp），截图做 sha256/并排附件供人复核；后续版本再考虑像素 diff。

### 2.3 新工具 `dwguard_aesthetic`（第 14 个工具）

| action | 作用 | 关键约束 |
| --- | --- | --- |
| `profile` | 读/写审美偏好档案；`list` 按 area 过滤 | 写入必须带 `source` 与 `confidence` |
| `baseline` | `save` 当前截图/布局树为基线；`list` 列出基线 | 只在有通过审计 + 用户确认后允许 save |
| `compare` | 用当前证据对比基线，输出数值 diff（含超阈值项） | 只读；输出可直接作为审美判据的 `actual` |
| `learn` | 从本轮确认/驳回/校准 miss 中**提议**档案增量与断言模板 | 只提议不落盘；`apply:true` 才写，且必须带用户确认 |

- 工具数变化：13 → 14；`apply` 注册的测试需同步（`apply.test.mjs`）；
- 与现有工具联动：`dwguard_spec` 验收标准可引用档案条目（`profileRef: "AES-PALETTE-01"`）；`dwguard_audit` 的审美 check 可引用 `compare` 输出作为 `actual`；`dwguard_confirm` 记录时触发 `learn` 建议。

### 2.4 学习闭环

```text
用户确认/驳回、审计 finding、calibration miss
        │
        ▼
dwguard_aesthetic learn（提议：新增/加权/降权/断言模板）
        │ 用户确认（apply）
        ▼
knowledge/aesthetic-profile.md（项目审美记忆）
        │
        ├─ dwguard_spec：生成/建议审美判据（profileRef）
        ├─ dwguard_audit：compare 基线 → actual（数值）
        └─ 下一轮：基线回归 + 偏好复用
```

约束：

- **不自动改用户需求**：`learn` 只提议，写入需 `apply:true` 且来自用户确认；
- **可解释**：每条决策记 `source`（第几轮确认/哪条 finding/哪次 miss）；
- **可撤销**：`profile` 支持 `remove`，保留审计追溯（不物理删除，标 `superseded`）。

### 2.5 验收标准（可证伪）

| ID | 判据 | 验证方式 |
| --- | --- | --- |
| AEST-A | `aesthetic profile` 写入后可从磁盘读回，字段完整（id/area/decision/source/confidence） | 单测：写读一致 |
| AEST-B | `learn` 只提议不落盘：未确认时档案不变，返回 proposals | 单测：调用后读文件对比 sha256 |
| AEST-C | `apply` 后 confidence 变化符合规则（确认 +0.1 / 驳回 −0.2，夹在 0–1） | 单测：多轮加减 |
| AEST-D | `baseline save` 需要「通过审计 + 用户确认」，否则拒绝 | 单测：缺确认 → 拒绝 |
| AEST-E | `compare` 对超出阈值（间距 ±2vp / 字号 0 / 圆角 ±2vp）的项给出 fail 列表 | 单测：构造 bounds 差异 |
| AEST-F | 审美 check 引用 `profileRef` 但档案不存在 → 审计闸门拒绝 | 单测：error 文案 |
| AEST-G | 报告渲染审美档案引用与基线差异列 | 单测：markdown 断言 |

## 3. 兼容性与迁移

- `devicePool` 空配置 = 0.5.0 行为，老任务包/老工作区不受影响；
- `checks[].device` 可选，只有启用池才强制；
- 审美档案/基线都是**新增目录**，不修改 `spec.json` 结构；`profileRef` 为可选字段；
- 工具数 13 → 14：`apply` 与注册测试同步更新；README/技能文件同步；
- 版本语义：新增配置 + 新工具 = `0.6.0`（minor）。

## 4. 版本计划

| 版本 | 内容 | 状态 |
| --- | --- | --- |
| `0.6.0` | P3 设备池 + 审美学习 v1（profile/baseline/compare/learn + `dwguard_aesthetic`） | 本计划 |
| `0.6.1` | 像素级截图 diff（独立工具/可选依赖）、审美规则候选入库 | 后续 |

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 模拟器并发导致性能取证失真 | 默认串行；性能判据独占设备；并发仅允许真机且告警 |
| 审美档案变"个人口味大杂烩" | 每条带 area/source/confidence；只从用户确认学习；`learn` 提议需 apply |
| 基线过期（设计改版） | 基线按 `specVersion` 隔离；`compare` 提示"基线版本 != 当前 specVersion" |
| 工具膨胀 | 只加 1 个工具（`dwguard_aesthetic`），其余能力挂现有工具参数 |
| 截图 diff 依赖 | v1 只做布局树数值 diff，像素 diff 留 0.6.1（可选依赖） |

## 附录：与官方 DevEco 流程的差异（本插件多出来的部分）

官方 DevEco 链路（DevEco Code 的 Build/Plan/Goal 模式 + DevEco Studio 构建/预览/Profiler + DevEco Testing/Hypium + AGC 审核）强在**工具能力**；本插件不加工具，加的是**验收与追溯层**：

| 官方能力/做法 | 插件增量 |
| --- | --- |
| Goal 模式在对话里端到端交付，验证标准随对话 | **冻结任务包**：四维可证伪判据 + 规则引用 + 版本号，落盘 `spec.json/md` |
| Agent 自测、可选 UI 检查（多模态语义判断） | **外部审计**：DSH 自己取截图/布局树/日志/测量，证据包 sha256；自验不作为通过依据 |
| 没有派发前独立审查 | **对抗预审**：性能/生命周期/并发/API 兼容/验收可行性，阻断项必须反驳且关闭 |
| 单会话、单执行者 | **协作协议**：Goal 简报 + outbox 回执/交付/卡住看门狗 + 跨轮隔离 |
| 编码期无独立巡检 | **影子审查**：增量静态扫描 + UI 树 + 风险分层，结构性风险停线 |
| 测试靠 Hypium/DevEco Testing（工具） | 把测试/工具调用变成**证据源**，进入四维审计与报告 |
| 没有机器可判的验收 | `0.5.0` **断言重算**：`actual` vs `assertion`，矛盾拒绝；报告含 `assertionVerdict` |
| 没有返工闭环 | **闸门 + 返工单**：must 全覆盖、四维评估、无 blocker；失败自动出返工单 |
| 没有跨轮学习 | **校准账本 + 知识沉淀**；`0.6.0` 再加**审美学习**（档案/基线/提议） |
| 上架前检查靠人工 | **规则目录 75 条**（含 AGC 隐私 9 条）+ 官方语料检索 + 扫描规则 ID |
| 报告以 UI/日志为主 | **机器可读报告**（audit.json / acceptance-report.md）可被 CI/回归消费 |

官方有而插件不做的：IDE 编辑体验、预览器/Profiler GUI、代码补全、真机调试器、应用市场发布流程本身。插件定位是**编排者 + 验收者**，把这些工具当证据源调用。
