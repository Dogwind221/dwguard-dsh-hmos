# 0.6.0 计划：内存感知的设备矩阵（P3）+ 审美学习

> 状态：**方案（待实现）** · 目标版本：`0.6.0` · 前置：`0.5.0`（断言化 + 取证剧本 + 交互轨迹）
> 范围：P3（读配置 + 读主机内存的设备矩阵）+ 审美学习 v1（偏好档案 / 视觉基线 / 学习闭环）。

## 0. 为什么是这两件事

`0.5.0` 解决了「判据可执行」（assertion + actual）和「证据怎么取」（剧本 + 交互轨迹）。还剩两个结构性缺口：

1. **单设备假设**：`dwguard_audit` 只记录一轮检查，不记录「在哪些设备/屏幕族/API/字体档上取的证」；多设备矩阵只能靠人肉串行，结果无法机器复核。
2. **审美维度没有记忆**：功能/性能/无障碍可以靠断言和数值回归，审美判据（间距、圆角、字号阶、配色、密度、动效）每轮重新争论；用户确认过的选择没有沉淀，`dwguard_calibration` 只能统计漏检率，不能改进行为。

0.6.0 的目标：**设备维度按主机内存自动升降级、按华为屏幕族做适配矩阵；审美判断有档案、有基线、能从用户反馈中学习。**

## 1. P3：内存感知的设备矩阵

### 1.1 设计原则

- **读用户配置 + 自动探测主机内存**：配置优先，缺省用 `os.totalmem()`；CI/容器里可用 `hostMemoryGb` 覆盖；
- **16GB 机器只做单机验证**，≥32GB 才允许矩阵验证（用户策略，代码里固化为默认闸门）；
- **子代理并行、设备操作串行/限额**：矩阵是多台设备按屏幕族轮转，不是无限并发；
- **屏幕族是矩阵的第一等公民**：直板机 / 阔折叠 / 双折叠 / 三折叠；模拟器镜像类型直接映射；
- **设备身份进证据**：每条 check 记录 `device + family`，性能判据强制独占直板机。

### 1.2 配置与数据模型

```jsonc
// 插件配置（cordis.patch.yml 的 config 段）
{
  "hostMemoryGb": 0,                    // 0 = 自动探测；>0 = 手动覆盖（CI/容器）
  "deviceMode": "auto",                 // auto（按内存）| single | matrix
  "matrixMinMemoryGb": 32,              // 低于该值强制单机
  "deviceMatrix": ["phone", "widefold", "foldable", "triplefold"],
  "matrixScope": {
    "function":      ["phone"],                                     // 功能只跑直板机
    "performance":   ["phone"],                                     // 性能只用直板机（噪声最小）
    "aesthetic":     ["phone", "widefold", "foldable", "triplefold"],// 审美要全族看适配
    "accessibility": ["phone", "widefold", "foldable", "triplefold"] // 无障碍要全族看触控/字号
  },
  "allowMissingMatrixFamilies": false,  // true = 缺族降级为警告（写明原因），否则闸门拒绝
  "devicePool": [
    { "sn": "127.0.0.1:5555", "family": "phone",     "apiLevel": 24, "kind": "emulator" },
    { "sn": "127.0.0.1:5557", "family": "widefold",  "apiLevel": 24, "kind": "emulator" },
    { "sn": "127.0.0.1:5559", "family": "foldable",  "apiLevel": 24, "kind": "emulator" },
    { "sn": "127.0.0.1:5561", "family": "triplefold","apiLevel": 24, "kind": "emulator" }
  ],
  "maxConcurrency": 0,                  // 0 = 自动（见 1.3）
  "deviceLockTimeoutMs": 600000
}
```

**屏幕族 ↔ 模拟器镜像映射**（`devecocli emulator image list` 实测支持的类型）：

| 屏幕族 | 中文 | device type | 适配关注点 |
| --- | --- | --- | --- |
| `phone` | 直板机 | `phone`（Pura 90） | 单栏布局、48vp 触控、大字体不破版 |
| `widefold` | 阔折叠 | `widefold` | 展开双栏、折痕区避让、横向利用率 |
| `foldable` | 双折叠 | `foldable`（Mate X7） | 折叠/展开切换、断点、动效连续性 |
| `triplefold` | 三折叠 | `triplefold` | 三种形态、分栏与状态保持 |

真机按 `kind: "real"` 入池，同样按 `family` 归类，可替代对应模拟器。

### 1.3 内存策略（核心）

| 主机内存 | `deviceMode` 实际取值 | 行为 |
| --- | --- | --- |
| `< 32GB`（如 16GB） | `single` | 只允许 1 台设备（默认直板机）；`deviceMatrix` 被忽略并输出警告；审美/无障碍也只在这一台取证 |
| `>= 32GB` | `matrix` | 按 `matrixScope` 跑多族矩阵；并发 = `min(maxConcurrency||2, 设备数, floor((hostMemoryGb - 8) / 3))` |

- 单台模拟器按 **3GB** 预算（实测 Pura 90 工作集 2.7GB），预留 8GB 给系统/DSH；
- `maxConcurrency` 上限 4；模拟器并发时性能判据仍独占（矩阵轮转，不在性能取证期间并发）；
- 内存不足时**降并发并警告**，不静默失败；`hostMemoryGb` 是显式覆盖，便于 CI 复现。

### 1.4 行为

1. `dwguard_deveco` 新增 `device` 参数（缺省 = 直板机空闲设备）；`device` 动作返回 `{hostMemoryGb, deviceMode, pool[]}`；
2. `dwguard_audit` 的 `checks[]` 新增 `device` + `family`（matrix 模式必填）；
3. 闸门按 `matrixScope` 校验覆盖：审美/无障碍缺任一族 → error（`allowMissingMatrixFamilies=true` 时降级警告并写进报告）；
4. 报告与 manifest：`audit.json` 记 `devices[]`（sn/family/apiLevel/kind/fontScale/theme）；验收报告出「判据 × 屏幕族」矩阵；
5. `dwguard_status` 显示：主机内存、生效模式、覆盖缺口、设备队列。
6. 性能判据在 `family=phone` 且设备独占时取证；矩阵模式下性能只是"直板机单点"，不做跨族性能对比（避免模拟器噪声）。

### 1.5 验收标准（可证伪）

| ID | 判据 | 验证方式 |
| --- | --- | --- |
| P3-A | `hostMemoryGb=16` → 生效 `single`，矩阵配置被忽略且输出警告 | 单测：配置解析 + 假内存注入 |
| P3-B | `hostMemoryGb=32` → 生效 `matrix`，`allowMissingMatrixFamilies=false` 时缺族被闸门拒绝 | 单测：配置 + audit 缺 widefold，断言 error |
| P3-C | `deviceMode=single/matrix` 手写覆盖优先于内存推断 | 单测：三组配置断言 |
| P3-D | `matrixScope` 生效：function/performance 只查 phone，aesthetic/accessibility 查全部四族 | 单测：矩阵覆盖表 |
| P3-E | 并发自动计算：16GB→1；32GB→2；64GB→4（受设备数封顶） | 单测：并发函数 |
| P3-F | 设备锁：串行执行、超时释放并警告 | 单测：假 clock + 锁文件 |
| P3-G | 报告含「判据 × 屏幕族」矩阵与 `devices[]` manifest | 单测：读 acceptance-report.md / audit.json |
| P3-H | 模拟器并发时性能判据拒绝启动并发取证（独占令牌） | 单测：两个性能 task 并发 → 第二个排队/拒绝 |

## 2. 审美学习 v1（具体做法）

### 2.1 问题

- 审美判据（`DW-AES-*` 21 条）依赖人，每轮重新争论；
- 用户确认过的选择（主色、圆角、间距节奏、字号阶、深色模式策略、动效时长）没有记录；
- 截图对比靠肉眼，没有基线；「这轮比上轮丑了」无法回归；
- `dwguard_calibration` 的 miss 只统计，不反哺规则。

### 2.2 输入（学什么）

| 来源 | 例子 | 权重 |
| --- | --- | --- |
| 用户确认（`dwguard_confirm` accept） | "圆角用 20 更柔和" | 0.7 起步 |
| 用户驳回/返工理由 | "间距太挤了，改回 16" | 0.4（反向证据） |
| 审计审美 finding（用户接受） | `A-01` 间距 20vp 偏离基线 | 0.5 |
| `dwguard_calibration miss`（审美维） | "审计通过但用户觉得丑" | 0.6（风险条目） |
| 项目资源文件（冷启动种子） | `resources/base/element/color.json` / `float.json` | 0.6 |

**不学**：聊天里的随口评价、没有 `source` 的自由文本、执行者自述。

### 2.3 存储（三份文件）

```text
knowledge/
  aesthetic-profile.md        # 人类可读档案（表格）+ 末尾 JSON 块（机器可读）
  aesthetic-history.jsonl     # 追加式事件：proposed/applied/superseded/conflict
artifacts/visual-baseline/
  <specVersion>/
    index.json                # 页面/状态 → 文件 + 关键数值
    <page>.<state>.png        # 截图（人复核）
    <page>.<state>.bounds.json# 布局树数值：节点 id/bounds/fontSize/padding/radius/color
```

档案条目（写在 JSON 块里）：

```jsonc
{
  "id": "AES-RADIUS-01",
  "area": "radius",                 // palette|spacing|radius|type|density|motion|dark|icon|card
  "decision": "卡片圆角 20vp",
  "value": { "number": 20, "unit": "vp" },
  "source": "confirmation-3",       // 第几轮确认/哪条 finding/哪次 miss
  "evidence": ["artifacts/visual-baseline/3/index.json"],
  "confidence": 0.7,                // 0–1
  "status": "active",               // active|superseded
  "updatedAt": "2026-11-02T…"
}
```

### 2.4 提取规则（确定性，不靠模型猜）

`dwguard_aesthetic learn` 对每轮输入做一次确定性抽取：

1. **数值**：正则 `(\d+(?:\.\d+)?)\s*(vp|dp|px|pt|ms|%|deg)?`；**颜色**：`#[0-9A-Fa-f]{6}`；
2. **领域映射**（关键词 → area）：色/主色/强调色/品牌色 → `palette`；间距/留白/margin/padding/gap → `spacing`；圆角/radius → `radius`；字号/字重/行高 → `type`；密度/紧凑/宽松 → `density`；动效/时长/缓动/ms → `motion`；深色/暗色/夜间 → `dark`；图标 → `icon`；卡片/列表行 → `card`；
3. **候选合并**：同 `(area, 值, 单位)` 只留一条，`confidence` 按 2.5 累加；同 area 不同值 → 生成 `conflict` 提议（列出新旧值与来源），**不覆盖**；
4. **冷启动**：无档案时，先读项目 `resources/base/element/color.json` / `float.json` 抽 `palette` / `spacing` / `radius` 作为种子（`source: "project-resources"`，confidence 0.6）。

### 2.5 提议 → 用户确认 → 应用

```text
learn（默认）: 只返回 proposals，不写文件
   { proposals: [ {id, area, decision, value, confidence, reason, sources[] } ],
     conflicts: [ {area, candidates[{value, sources}], question} ] }

apply:true（必须带用户确认）:
   - 无冲突条目：写档案（新条目或 confidence 累加）
   - 冲突条目：要求用户在对话里选一个（`dwguard_aesthetic apply` 带 `choice`），把落选值标 superseded
   - 追加 aesthetic-history.jsonl，版本号 +1
```

**置信度规则**：确认 +0.1、驳回 −0.2、重复证据 +0.05；夹在 0–1；≥0.8 视为"稳定偏好"（spec 默认引用），<0.3 保留但不推荐。

### 2.6 消费（学完之后怎么用）

1. **写任务包时（`dwguard_spec`）**：审美判据可带 `profileRef: "AES-RADIUS-01"`；插件对已存在的同 area 偏好给出提示（`W_AEST_PROFILE_HINT`），**只建议不代写**；
2. **审计时（`dwguard_audit`）**：审美 check 可引用 `profileRef`；`profileRef` 不存在 → 闸门 error；`compare` 的输出直接作为 `actual`（如 `"圆角 20vp"`），配 `assertion: { matcher: "range", min: 18, max: 22, unit: "vp" }`；
3. **确认时（`dwguard_confirm`）**：accept 后触发 `learn` 建议（不自动 apply）；验收报告追加「审美增量」小节（本轮确认/变更了哪些偏好）；
4. **下一轮**：`compare` 用新基线 + 档案判据回归；用户改口时旧条目 `superseded`，历史可追溯。

### 2.7 基线回归（不靠图像库）

- `baseline save`：**只允许在「有通过审计 + 用户确认」之后**，把本轮截图与 `bounds.json` 存进 `artifacts/visual-baseline/<specVersion>/`；
- `compare`：对同一页面/状态读当前 `bounds.json` 与基线比较：
  - 间距/圆角：±2vp 内通过，超出按倍数定 `major`/`minor`；
  - 字号：0 容忍；
  - 颜色：hex 精确比较（token 归一化后）；
  - 截图：sha256 不同即提示"需人工并排复核"，不当自动失败；
- 基线版本与当前 `specVersion` 不一致时输出警告（设计改版要显式重建基线）。

### 2.8 完整示例

> 第 2 轮用户确认时顺口说：「卡片圆角 16 太方了，用 20，间距保持 12。」

1. `dwguard_aesthetic learn` 抽取：`radius=20vp`（确认，0.7）、`spacing=12vp`（确认，0.7 与已有 12 合并 → 0.8）；
2. 返回 proposals，不落盘；
3. 用户确认后 `apply:true`：档案新增 `AES-RADIUS-01=20vp`、`AES-SPACING-01=12vp(0.8)`；
4. 下一轮 `dwguard_spec`：审美判据提示 `W_AEST_PROFILE_HINT`，建议 `A-02 卡片圆角 20vp（profileRef AES-RADIUS-01）` + `assertion range 18–22 vp`；
5. `dwguard_audit`：审美子代理跑 `compare`，`actual="20vp"`，断言通过；报告写「profileRef AES-RADIUS-01 · 基线一致」；
6. 若下轮有人改成 24vp：`compare` 超差 → `A-02` finding；用户说"24 更好" → `learn` 出 **conflict**，用户选 24 → 20 标 `superseded`，历史留痕。

### 2.9 工具 `dwguard_aesthetic`（第 14 个工具）

| action | 作用 | 约束 |
| --- | --- | --- |
| `profile` | `list` / `get` / `write` / `remove` 审美档案 | 写入必须带 `source`+`confidence`；remove 只标 superseded |
| `baseline` | `save` / `list` 视觉基线 | save 需通过审计 + 用户确认 |
| `compare` | 当前证据 vs 基线，输出数值 diff | 只读；输出可直接作 `actual` |
| `learn` | 从本轮输入提议档案增量/冲突 | 默认不落盘；`apply:true` 才写 |

### 2.10 验收标准（可证伪）

| ID | 判据 | 验证方式 |
| --- | --- | --- |
| AEST-A | 档案写入/读回字段完整（id/area/decision/value/source/confidence/status） | 单测：写读一致 |
| AEST-B | `learn` 默认不落盘（档案 sha256 不变），只返回 proposals | 单测 |
| AEST-C | 置信度规则：确认 +0.1 / 驳回 −0.2 / 重复 +0.05，夹 0–1 | 单测：多轮加减 |
| AEST-D | 同 area 不同值 → 返回 conflict，不覆盖旧值 | 单测 |
| AEST-E | `apply` 冲突必须带 `choice`，落选值标 superseded 且写 history | 单测 |
| AEST-F | `baseline save` 缺「通过审计 + 用户确认」→ 拒绝 | 单测 |
| AEST-G | `compare` 阈值：间距/圆角 ±2vp、字号 0、颜色精确；超差出 fail 列表 | 单测：构造 bounds 差异 |
| AEST-H | `spec` 引用不存在的 `profileRef` → 审计闸门 error | 单测 |
| AEST-I | 冷启动从项目 `color.json/float.json` 抽种子（palette/spacing/radius） | 单测：最小资源样例 |
| AEST-J | 报告渲染 `profileRef` 与基线差异列 | 单测：markdown 断言 |
| AEST-K | 档案无 `source` 的写入被拒绝（防"模型自嗨"） | 单测 |

### 2.11 不做什么

- 不做像素级审美评分（0.6.1 再考虑可选像素 diff）；
- 不用模型自动改用户需求/判据；
- 不跨项目共享审美偏好（项目级档案；跨项目复制需手动）；
- 不把"用户没说的话"当偏好（无 source 不写）。

## 3. 兼容性与迁移

- `devicePool` 空 + `deviceMode: single` = 0.5.0 行为；老任务包/老工作区不受影响；
- `checks[].device/family` 可选，只有 matrix 模式强制；
- 审美档案/基线是新增目录；`profileRef` 可选字段；
- 工具数 13 → 14：`apply` 与注册测试同步；README/技能同步；
- 语义化版本：新增配置 + 新工具 = `0.6.0`（minor）。

## 4. 版本计划

| 版本 | 内容 |
| --- | --- |
| `0.6.0` | P3 内存感知矩阵 + 审美学习 v1（profile/baseline/compare/learn + `dwguard_aesthetic`） |
| `0.6.1` | 可选像素级截图 diff、审美规则候选入库、矩阵批量排程（夜间/CI） |

## 5. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 16GB 机器跑矩阵导致卡死 | 内存闸门：<32GB 强制 single；并发按内存预算计算并降级警告 |
| 模拟器并发污染性能取证 | 性能判据只跑直板机 + 独占令牌；矩阵轮转不并发 |
| 审美档案变成"个人口味大杂烩" | 每条带 area/source/confidence；只从用户确认学习；冲突必须用户裁决 |
| 基线过期（设计改版） | 基线按 `specVersion` 隔离；compare 提示版本不一致 |
| 学习不可解释 | 所有提议带 source/evidence；history 追加式；可 supersede 不删除 |
| 工具膨胀 | 只加 1 个工具（`dwguard_aesthetic`），其余挂现有工具参数 |

## 附录：与官方 DevEco 流程的差异（本插件多出来的部分）

官方 DevEco 链路（DevEco Code 的 Build/Plan/Goal 模式 + DevEco Studio 构建/预览/Profiler + DevEco Testing/Hypium + AGC 审核）强在**工具能力**；本插件不加工具，加的是**验收与追溯层**：

| 官方能力/做法 | 插件增量 |
| --- | --- |
| Goal 模式在对话里端到端交付，验证标准随对话 | **冻结任务包**：四维可证伪判据 + 规则引用 + 版本号，落盘 `spec.json/md` |
| Agent 自测、可选 UI 检查（多模态语义判断） | **外部审计**：DSH 自己取截图/布局树/日志/测量，证据包 sha256；自验不作为通过依据 |
| 没有派发前独立审查 | **对抗预审**：性能/生命周期/并发/API 兼容/验收可行性，阻断项必须反驳且关闭 |
| 单会话、单执行者 | **协作协议**：Goal 简报 + outbox 回执/交付/卡住看门狗 + 跨轮隔离 |
| 编码期无独立巡检 | **影子审查**：增量静态扫描 + UI 树 + 风险分层，结构性风险停线 |
| 测试靠 Hypium/DevEco Testing（工具） | 把测试/工具调用变成**证据源**，进入四维审计与报告 |
| 没有机器可判的验收 | `0.5.0` **断言重算**：`actual` vs `assertion`，矛盾拒绝；报告含 `assertionVerdict` |
| 没有返工闭环 | **闸门 + 返工单**：must 全覆盖、四维评估、无 blocker；失败自动出返工单 |
| 没有跨轮学习 | **校准账本 + 知识沉淀**；`0.6.0` 再加**审美学习**（档案/基线/提议/冲突裁决） |
| 上架前检查靠人工 | **规则目录 75 条**（含 AGC 隐私 9 条）+ 官方语料检索 + 扫描规则 ID |
| 报告以 UI/日志为主 | **机器可读报告**（audit.json / acceptance-report.md）可被 CI/回归消费 |

官方有而插件不做的：IDE 编辑体验、预览器/Profiler GUI、代码补全、真机调试器、应用市场发布流程本身。插件定位是**编排者 + 验收者**，把这些工具当证据源调用。
