# 1.0.6 外部项目扫描记录（2026-11-22）

用三个真实的第三方鸿蒙工程检验 `dwguard_scan` 的规则，把误报转成回归用例。
这三个工程都不是本项目自己造的，代码由别人（或别的工具）写，正好用来暴露规则里的
「想当然」。

## 样本

| 样本 | 规模 | 来源 |
| --- | --- | --- |
| WindwindLure | 40 个 `.ets` / `.ts`，8024 行 | 真实鸿蒙应用（社区页、装备页、钓点页等） |


## 三个误报（已修 + 已加回归用例）

1. **STATE-NESTED-01 把比较当赋值**（3/3 误报）。
   `PhotoViewerPage.ets:63` 的 `this.post.imageColors.length === 0`、
   `PostDetailPage.ets:41`、`FishDetailPage.ets:169` 都是只读比较，被当成
   「嵌套属性被赋值，UI 不会刷新」。修法：赋值号两侧排除比较运算符
   （`(?<![=!<>])=(?!=)`），`+=` 这类复合赋值仍然会报。
2. **A11Y-TEXT-001 把 `@Builder bottomButton()` 当成 `Button(`**。
   `TournamentDetailPage.ets:110` 是一个构建函数名，不是按钮。修法：`\bButton\s*\(`。
3. **PERF-LIST-FOREACH 是文件级判定**：只要文件里出现过 `List(`，文件里所有
   `ForEach(` 都会被报。`GearPage.ets` 因此被指到 171 行的四标签 Tab（在 `Row` 里），
   而真正的 `List` 在第 187 行。修法：按花括号区间判断 `ForEach` 是否真的落在
   `List` / `Grid` / `WaterFlow` 内，现在报 188 行，指对了。

回归用例在 `tests/scan.test.mjs`：`scan ignores real-world false positives` 与
`PERF-LIST-FOREACH points at the loop inside the container, not a header loop`。

## 仍然留在报出的 29 条（按性质分）

- **A11Y-TEXT-001 × 22（warn）**：规则是文件级的——文件里有可点击控件、全文没有
  任何 `accessibility*` 调用就报一条。
  - 真阳性示例：`RaisedSpotButton.ets:95` 是纯图标凸起按钮（无文本子节点），
    读屏确实拿不到名字。
  - 噪声示例：`LightTabBar.ets:67` 的可点击 `Column` 里有 `Text(...)` 子节点，
    读屏本来就能朗读。
  - 下一版建议：只对「无可读文本子节点」的可点击控件报，而不是按文件判定。
- **PERF-LIST-FOREACH × 7（warn）**：全部落在 `List` 内的 `ForEach`
  （CommunityPage:289、TournamentPage:201、FishDexPage:265、FriendsPage:180、
  GearPage:188、ProfilePage:262、SpotListPage:157），是真阳性；这一类 feed / 列表
  页建议改 `LazyForEach` + `IDataSource`。
- **STATE-NESTED-01 × 0**：修复后不再误报，样本里也没有真实的嵌套赋值缺陷。

## 结论

- 三个真实工程里，规则一共报出 34 条，其中 3 条是明确误报（8.8%），已修。
- 没有发现真实的功能性缺陷（STATE 类），说明这两个应用的状态用法是对的；
  剩下的 29 条都是性能/无障碍建议。
- 这一步的实际收益不是「发现了多少 bug」，而是**规则在别人代码上的误报率被压到
  可接受范围**，且每个误报都变成了一条回归用例。
